# 智能家居课程设计执行方案

> 依据：`2026智能家居系统-课程设计指导书-学生用.docx`。本文提炼指导书要求，并结合“四人小组”给出可执行拆分；没有补写指导书之外的业务事实。

## 本次检查｜第 10 周架构评审

教师已确认本次检查为架构评审。现场用“一盏客厅灯”讲清五层职责、依赖方向和关键接口。第 13 周再演示可运行的建图、布放、控制及状态查询。

1. 说明需求和目标。住户回家、离家或睡觉时，需要逐个调灯、空调和其他设备。系统提供平面图控制和一键场景。
2. 介绍技术方案。采用 Home3D 路线 B，复用平面图及 3D 编辑能力。团队实现后端存储、设备控制、实时状态和场景策略。演示先用设备模拟器。
3. 展示[五层架构图](architecture.md#five-layers-and-deployment)及关键接口。讲清展示层提交意图、策略层生成命令、控制层校验和下发、设备层执行并上报、数据层持久化。
4. 用开灯命令走查接口。成功时由控制层保存已确认状态并推送给前端。超时时保留上次确认状态，并显示本次命令的超时结果。
5. 汇报四人分工及第 13 周目标。按进度表准备可行性报告、需求规格 v1.0、架构图和原型草图。

## 1. 项目边界与完成标准

系统面向单个家庭，必须交付一个浏览器访问的 Web 应用，包含前端与后端，数据能够持久化，并跑通以下主线：

`建图 → 布家具 → 控制设备 → 查看状态 → 触发场景`

最低完成标准：

- 五项必做功能 F1～F5 全部可用，而非只有页面或静态演示；
- 数据刷新、服务重启后不无故丢失；
- 五层架构职责与单向依赖可以讲清，设备模拟器可替换为真实设备；
- 完成需求、设计、测试、用户手册、演示视频和答辩材料；
- 至少用一套完整数据完成验收，并能在空白环境中即兴演示；
- 新增设备类型或即兴修改一个场景、阈值时，不需要改核心业务代码。

明确不要求：手机 App、小程序、原生客户端、真实硬件、多租户和商业化能力。鼓励提高项为三维可视化、多用户权限和 E1～E4。

## 3. 四人分工

所有成员都必须参与编码或可执行测试代码，不能只写文档。每周至少进行一次跨成员代码互评并留存记录。

| 成员 | 主责 | 主要编码与交付 | 关键验收 |
|---|---|---|---|
| A：组长/架构与集成 | 需求边界、五层架构、接口契约、进度、集成与发布 | 仓库骨架、统一异常与日志、接口约定、启动脚本、集成版本、架构文档 | 接口有契约；依赖不反向；主分支可运行；每周完成联调 |
| B：前端与空间可视化 | Home3D 接入、平面图/3D、家具库交互、控制面板和状态看板 | Home3D Fork 适配、store 持久化适配器、拖放/旋转/编辑、状态图层、历史曲线 | 创建房间、画墙、布家具；刷新恢复；同一状态三处一致 |
| C：后端、数据与设备控制 | 数据模型、API、持久化、实时推送、设备模拟器、命令链路 | 数据库脚本、REST API、WebSocket、设备能力抽象、模拟器、超时/重试/状态回写 | 命令端到端不超过 1 秒；失败、超时和重试可观察；新增设备类型不改核心代码 |
| D：策略、质量与文档统筹 | 规则引擎、场景、季节温控、测试策略、文档统筹和答辩材料 | 策略模块、场景配置、1℃ 滞回、环境自适应、自动化/接口测试、测试报告、用户手册 | 三个场景可执行；温度计算不写死；测试可重复；答辩可解释取舍 |

文档按“谁负责模块、谁写对应章节”拆分，D 只负责格式和版本统筹，不能替代其他成员撰写或实现其模块。

### GitHub 协作要求

- 组长邀请其余三名组员加入 [Smart Home 仓库](https://github.com/bagtyyarkovusov/smart-home)。进入 **Settings → Collaborators → Add people**，输入三人的 GitHub 用户名。邀请接受后，三名组员应能向仓库推送各自的分支并提交 PR。
- 每人从最新的 `main` 建立自己的功能或文档分支，例如 `feat/home3d-persistence`、`feat/device-control`、`feat/scene-strategy`。提交 PR 到 `main`，说明对应需求、改动和验证方法。
- 每个 PR 合并前至少由一位其他组员评审；组长协调合并和联调。每周至少完成一次集成和跨成员代码互评，保留 PR 记录。

## 6. 工作流

### 6.1 产品主流程

`家庭画像与痛点 → 用例与 MoSCoW → 五层架构和接口契约 → 建图/家具纵向切片 → 设备控制与状态 → 场景策略 → 性能与异常测试 → 演示交付`

### 6.2 代码依赖方向与运行时数据流

**代码依赖：展示层 → 策略层 → 控制层 → 设备层。** 数据层通过接口供各层按需使用。策略层通过读取接口获取规则或环境数据，由数据层负责数据库访问。手动控制虽然使用设备命令 API，也先进入策略层，由它生成单条命令计划。

**运行时反馈：** 设备通过控制层调用的设备接口返回结果。控制层先保存已确认状态，再广播。展示层通过 WebSocket 把更新转给浏览器。返回结果和推送都是运行时数据流，代码依赖仍然单向。

`用户操作（展示层） → API 校验 → 策略层求值 → 控制层编排/重试 → 设备层或模拟器执行 → 状态回写数据层 → WebSocket 广播 → 前端统一更新`

约束：

- 展示层不直接写 SQL，也不实现业务规则；
- 策略层回答“该做什么”，不直接操作数据库；
- 控制层回答“如何可靠执行”，不写季节温控规则；
- 设备层只知道能力与命令，不感知房间和用户；
- 数据层只负责持久化和查询；
- 前端只投影服务端状态，不把本地乐观更新当作最终事实。

### 6.3 开发与评审流程

1. 从已冻结的接口契约创建 feature 分支；
2. 先完成一个可演示纵向切片，再接第二个模块；
3. 每项功能同时提交自动化测试和手工验收步骤；
4. 每周合并已评审的 PR 到 main，联调主流程、异常流程和性能基线；
5. 代码互评记录模块边界、越层依赖、硬编码和异常处理；
6. 里程碑未通过时只修复阻塞项，不带病扩展新功能；
7. 第 15 周冻结代码，第 16 周只做演示和提交准备。

| 演示 | 屏幕录制工具、PPT 工具 | 两套演示数据、备用录屏、答辩问题清单 |

Home3D 当前参考版本使用 Vite 8，其 Node.js 要求为 `^20.19.0 || >=22.12.0`。团队统一使用 Node.js 22.12 或更高版本。演示阶段以设备模拟器为基线。

## 8. 推荐的首个迭代切片

为降低四人并行开发的集成风险，第一版只打通：

`创建一个房间 → 画一段墙 → 放置一盏灯 → 切换灯开关 → 在三个位置看到相同状态 → 保存并刷新恢复`

该切片验收后，再扩展家具旋转、历史曲线、三个场景和季节温控。这样可以先锁定坐标、API、状态同步和 Home3D 适配这四个高风险接口。
